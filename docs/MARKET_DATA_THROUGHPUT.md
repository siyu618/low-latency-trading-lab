# Experiment 03 Phase 3A — Integrated Market-Data Pipeline: Throughput Baseline

Canonical dataset: `docs/results/market-data-throughput/`
Benchmark: `benchmark/market_data_pipeline_throughput_bench.cpp`
Runner: `scripts/market-data-throughput.sh`
Analyzer: `scripts/analyze-market-data-throughput.py`

**Status: Phase 3A — Integrated Throughput Baseline: IMPLEMENTED / MEASURED.**
Phase 3 is **NOT** complete. Phase 3B (per-message latency and percentiles) is
**not started** and is deliberately absent from this document and this dataset.

---

## 1. WHY — the question Phase 3A is allowed to ask

### 1.1 Research question

> What steady-state **end-to-end message throughput** does the integrated
> market-data path sustain under a deterministic, valid, live-update workload?

Phases 1A and 1B verified the sequencer and the wire decoder **single-threaded**.
Phase 2 verified that the same correctness survives a **thread boundary and a
queue**. None of those measured rate, because none of them was allowed to read a
clock on the hot path.

Phase 3A is the first measurement of the **composed** system. It answers one
question — how fast does the whole path go — and it answers it once, for one
configuration, on one host.

### 1.2 What this measurement includes

The number reported here is:
`live messages consumed / elapsed_ns`, where `elapsed` runs from the release of
the start gate to the consumer's final apply.

Inside that interval, every one of these stages runs and every one of them is
included:

| stage | what it does |
|---|---|
| source chunking | the producer takes a 64 KiB span of the pre-generated byte stream |
| framing (`StreamDecoder`) | splits chunks into frames across chunk boundaries, carrying partial frames |
| binary decode (`decode_one`) | frozen Phase-1B wire decode into an `MdMessage` |
| push (`try_push` + retry) | handoff into the SPSC ring, retrying while full |
| pop (`try_pop` + retry) | dequeue, retrying while empty |
| sequencing (`MarketDataPipeline::apply`) | sequence validation, staging bookkeeping, counters |
| book apply (`FlatOrderBook::apply`) | level update/delete, best-price maintenance |

It **is** the cost of the composition, under one chunk policy and one queue
capacity. It is **not** the cost of any single component, and it is not the sum
of the components' individually-measured costs — the composition has its own
behaviour (§4.4).

### 1.3 What this measurement does NOT include, isolate, or claim

Deliberately outside the interval:

- synthetic workload generation, encoding, buffer growth and RNG
- the reference result and the expected checksum
- construction of the queue and the pipeline
- creation of either worker thread
- the ready handshake and the initial snapshot (§3.1)
- the `join()` of either thread
- all reporting

And deliberately **not claimed** anywhere in this document:

- **Not a latency, not a percentile, not a per-message cost.** The clock is read
  exactly twice per repetition, at session granularity. There is no per-message
  timestamp, no timestamp field on `MdMessage`, and no side timestamp array.
- **Not exchange throughput, not production trading throughput, not
  wire-to-exchange latency.** It is a synthetic workload on one host.
- **Not a comparison.** Phase 3A has one cell and compares nothing (§2.3).
- **Not a bottleneck attribution.** The retry counters are reported as
  diagnostics, and §4.4 explains why they do not license a causal claim.

### 1.4 Evidence labels used in this document

- **MEASURED** — read directly from the committed dataset.
- **DERIVED** — computed from the dataset by
  `scripts/analyze-market-data-throughput.py`.
- **REASONED** — argued from the measured data plus the frozen source. Not a
  measurement, and not presented as one.

## 2. WHAT — the system, the workload, the reported quantities

### 2.1 The system under test

```
pre-generated byte stream (145,003,736 bytes)
  -> StreamDecoder                  framing across 64 KiB chunk boundaries
  -> decode_one                     frozen Phase-1B wire decode
  -> MdMessage
  -> SpscSeparatedBaselineRingBuffer<MdMessage, 4096>
  -> MarketDataPipeline<FlatOrderBook>
```

**Every component is FROZEN.** The book is Experiment 01's, the queue is
Experiment 02's final selected SPSC variant
(`SpscSeparatedBaselineRingBuffer` — the uncached separated-cursor baseline),
and the framer, decoder, message vocabulary and sequencer are Experiment 03
Phases 1A/1B/2. Phase 3A integrates them. It modifies none of them, and **no
component was changed in order to move any number in this document.**

### 2.2 The workload

Deterministic, seeded, and generated **in full before any clock starts**.

| property | value |
|---|---|
| seed | `0x5EEDC0FFEE` |
| initial snapshot | `SnapshotBegin` + 64 bid levels + 64 ask levels + `SnapshotEnd` = 130 messages |
| mid price | 100000 |
| levels per side | 64 (128 price slots in total) |
| live messages | 5,000,000 `Level` messages |
| total messages | 5,000,130 |
| set / delete mix | 4,400,492 sets / 599,508 deletes (11.99% deletes) |
| price domain | `[1, 200000]` — `FlatOrderBook`'s default domain, so zero out-of-range updates |
| encoded size | 145,003,736 bytes (138.3 MiB) |
| 64 KiB chunks | 2,213 |

Each live message draws a side, then an offset in `[1, 64]` from the mid, giving
one of 128 price slots, and a quantity: with probability 12% a `qty = 0` delete,
otherwise a set of `qty in [1, 1000]`. Deleted slots are re-drawn shortly after,
which is what holds the level population steady.

**This does not model any specific real exchange's message distribution.** It is
a reproducible workload chosen so that the composed path runs continuously at a
stable level population, so that the measured rate describes steady state rather
than a transient.

Randomness uses `llmd::gen::uniform_below` (a hand-rolled `rng() % n`) rather
than `std::uniform_int_distribution`, whose mapping the standard leaves
implementation-defined. The workload is pinned by a golden checksum, so it must
reproduce byte-for-byte across standard libraries. The same rule is stated in
`market-data-pipeline/include/md_stream_gen.h`.

### 2.3 ONE canonical cell — there is no matrix here

| axis | value | is it an option? |
|---|---|---|
| source chunk size | 64 KiB, final chunk naturally shorter | **no** — compile-time constant |
| SPSC capacity | 4096 | **no** — compile-time constant |

The benchmark's argument parser **refuses unrecognised flags**, so
`--chunk-bytes` and `--capacity` cannot be smuggled in. This is deliberate: a
flag would make a treatment matrix possible by accident, and Phase 3A is a
baseline, not a comparison.

Phase 3A therefore does **not** compare, and no number here may be read as a
comparison of:

| not compared | where that comparison lives |
|---|---|
| cached vs baseline SPSC cursor | Experiment 02 Phase 3B, frozen |
| SameLine vs Separated cursor layout | Experiment 02 Phase 3A, frozen |
| `FlatOrderBook` vs `MapOrderBook` | Experiment 01, frozen |
| multiple queue capacities | a separate phase, not started |
| multiple chunk sizes | a separate phase, not started |

Chunk-size sensitivity in particular is a separate experiment. That the figure
includes framing under **one** chunk policy is part of the result, not a caveat
bolted onto it: framing cost is a function of how the transport slices the
stream, and a different chunk policy is a different measurement.

### 2.4 Reported quantities

**PRIMARY**

| quantity | definition |
|---|---|
| `elapsed_ns` | gate release → consumer's final apply, session granularity |
| `messages_processed` | live messages successfully consumed/applied inside the timed region (5,000,000) |
| `ns/message` | `elapsed_ns / messages_processed` |
| `messages/second` | `messages_processed · 10⁹ / elapsed_ns` |

**SECONDARY (diagnostics)**

| quantity | definition |
|---|---|
| `producer_full_retries` | failed `try_push` attempts inside the timed region |
| `consumer_empty_retries` | failed `try_pop` attempts inside the timed region |

Both retry counters are counted **only inside the timed region**. The retry
policy itself is Experiment 02's, unchanged: retry until success, count
consecutive failures, `yield()` after 1024 consecutive failures, reset the run
on any success, never sleep.

**Not reported, deliberately:** P50, P90, P99, P99.9, any per-message timestamp,
and any latency distribution. That is Phase 3B.

## 3. HOW — the measurement procedure

### 3.1 The timed region, exactly

The handshake is the repository's established two-thread idiom (see
`benchmark/spsc_throughput_bench.cpp`). Both worker threads are created first,
and **both must be parked before the clock starts**:

```
producer:  feed ONLY the snapshot bytes; drain nothing else
           producer_ready.store(true, release)
           spin on start.load(acquire)          <- parked
consumer:  pop EXACTLY 130 messages (the snapshot); apply each
           consumer_ready.store(true, release)
           spin on start.load(acquire)          <- parked
main:      wait for BOTH ready flags
           t0 = Clock::now()
           start.store(true, release)           <- THE GATE
producer:  ... observes the gate, feeds live chunks, frames, decodes, pushes ...
consumer:  ... observes the gate, pops, applies ...
consumer:  t1 = Clock::now()   immediately after the FINAL apply
main:      join both; elapsed = t1 - t0
```

Three consequences worth stating precisely:

- **`t1` is taken by the consumer thread itself**, immediately after its last
  apply — not by the main thread after `join()`. Stopping after `join()` would
  fold thread teardown into every repetition.
- **The gate is a store, not a barrier.** The interval opens at
  `start.store(...)`. Each thread enters its measured work when it *observes*
  that store, so each thread's gate-observation latency is inside the interval.
  Against a ~170 ms interval this is sub-microsecond, but it is included and is
  not described as zero.
- **The interval is not "producer finishes decoding".** It ends when the last
  message has been consumed and applied. A run that stopped when the producer
  finished would measure the decoder only.

**The initial snapshot is applied BEFORE the gate and is excluded from every
figure.** A small valid snapshot is required to bring the book to `LIVE` — the
pipeline refuses live updates while unsynced — but recovery and sync paths are
Phase 1/2 correctness territory, and §2 of the brief excludes them from a
steady-state throughput figure by construction. Because the producer feeds only
the snapshot bytes and then parks, and the consumer drains exactly the
snapshot's 130 messages and then parks, every byte fed after the gate is a live
Level update.

The timed region therefore contains: **no malformed bytes, no sequence gap, no
stale message, no snapshot recovery, no terminal decode error and no truncated
input.** The workload cannot produce one, and the validation in §3.3 would fail
the run if it did.

### 3.2 What is generated before the clock

Everything expensive is done up front, outside the interval:

1. the complete encoded byte stream (145 MB), built by the frozen encoder
2. the decoded message vector, produced by a full pass of the frozen framer
3. the single-threaded reference (`Observation`, §3.3)
4. the expected checksum
5. a full run of the frozen `ThreadedMdPipeline` over the same bytes (§3.3)
6. the queue and the pipeline objects
7. both worker threads, parked on the gate

### 3.3 Validation — every run, timed or not

A repetition that produced a wrong answer is not a slow repetition; it is not a
measurement at all. Before any clock starts:

1. **Whole-stream decode.** Every chunk must return `Ok`, and
   `framer.finish()` must return `Ok` — the Phase-2 finalization that makes
   truncated input visible. A non-`Ok` result aborts with exit 3: it means the
   generator or encoder is at fault, not the machine.
2. **Single-threaded reference.** The decoded messages are applied to a fresh
   `MarketDataPipeline<FlatOrderBook>` on one thread. This yields the reference
   `Observation`: state, `last_applied_seq`, `expected`, best bid, best ask,
   level count, all twenty counters, and an FNV-1a fold of all of them.
3. **Frozen-harness agreement.** The frozen `ThreadedMdPipeline` is run over the
   same bytes and must agree with (2) on **every observable and all twenty
   counters**. This is what licenses this file owning its own thread pair: the
   harness must own the threads to place the gate and `t1` where §3.1 requires,
   and the frozen Phase-2 composition is the oracle proving those loop bodies
   behave identically.

Then **every measured repetition** must satisfy all of:

```
terminal_error == false
decoded_messages == enqueued_messages == consumed_messages == 5,000,130
live messages consumed == 5,000,000
elapsed_ns > 0
state, last_applied_seq, expected, best_bid, best_ask, level_count,
every counter, and the folded checksum all equal the reference
```

A failing repetition is printed with its full state and the process exits 4.
It is **never** quietly dropped to make a median look better.

### 3.4 Anti-DCE

Every observable is folded into `sink`, `sink` is printed, the checksum is
printed and written to both output files, and the fold gates the process exit
status. A fold over the final book state cannot be computed unless the applies
really happened, and the exit contract makes the fold observable.

There is deliberately **no per-message fold**: adding one would change the
consumer loop being measured, and the loop under test is Phase 2's, unchanged.

### 3.5 Repetitions, sessions, and the published figure

- **Warm-up:** 1 excluded repetition per process. It runs the same timed
  machinery and its value is printed to stderr as a check, but it enters no
  published figure.
- **Measured repetitions:** 5 per process. **All 5 are preserved** in `raw/`.
- **Sessions:** 4, one process each, run back-to-back.

The published figure is the **per-session median of the 5 measured
repetitions**, then the **median across the 4 session medians**.

**Every raw repetition is preserved and none is discarded.** Repetitions are
never pooled into one giant observation: `ns/message` is a per-repetition
quantity and pooling 20 of them into one ratio would produce a number that no
single run ever exhibited.

**The four sessions are sequential and are NOT independent trials.** There is
one cell, so there is no AB/BA counterbalance to apply — a counterbalance needs
two treatments and Phase 3A has one. What the four sessions give is a direct
read on temporal drift: with the cell held fixed, all variation between session
medians is temporal, and §4.2 reports it rather than hiding it.

### 3.6 Reproducing the run

```sh
scripts/market-data-throughput.sh          # full canonical run (~4 s of measured time)
FORCE=1 scripts/market-data-throughput.sh  # overwrite the existing dataset
SMOKE=1 scripts/market-data-throughput.sh  # tiny, non-canonical, into BUILDDIR
```

The runner refuses to overwrite an existing dataset without `FORCE=1`, refuses
to start under a saturated host, and writes into
`docs/results/market-data-throughput/`. The analyzer is the authoritative gate:
it re-derives every headline from the raw rows, refuses the dataset if any
session disagrees with any other on workload or reference checksum, and refuses
it if any session's slowest repetition exceeds 5× its own fastest.

## 4. MEASURED — the canonical dataset

Measured 2026-09-15 on the Apple M3 Max development host (macOS 14.2.1, Apple
clang 15, Release, forced `-O3 -DNDEBUG`, no arch flags), 4 sessions × (1
excluded warm-up + 5 measured repetitions), 5,000,000 live messages per
repetition. Load average 3.08 at start, 3.16 at end, on 14 logical CPUs. Full
host metadata: `docs/results/market-data-throughput/HOST.md`.

**20 measured repetitions. All 20 `PASS`. All 20 produced the identical
reference checksum `0x7E6BA57E42B53319`.**

### 4.1 The published figure

| quantity | value |
|---|---|
| **`ns/message`** (median of session medians) | **34.909762** |
| **`messages/second`** (median of session medians) | **28,646,780.764** |
| `messages_processed` per repetition | 5,000,000 |
| elapsed per repetition | 167–188 ms |

A note on the two primary figures. They are each the median of their own
per-repetition series, and `median_messages_per_second ≠ 10⁹ /
median_ns_per_message`: the reciprocal of the median is not the median of the
reciprocals. Over all 20 repetitions the pooled reciprocals give 28,674,451.8,
about 0.1% away. Both numbers are reported as what they are — medians of their
own series — and neither is derived from the other.

### 4.2 Per-session medians and the temporal spread

| session | median `ns/message` | median `messages/second` | min | max |
|---|---|---|---|---|
| 1 | 34.102708 | 29,323,184.196 | 33.902833 | 35.161858 |
| 2 | 35.386125 | 28,259,663.922 | 34.660775 | 37.555858 |
| 3 | 35.162250 | 28,439,590.754 | 34.910242 | 37.533842 |
| 4 | 34.657275 | 28,853,970.775 | 33.443083 | 35.944575 |

Session medians span 34.10–35.39 ns/message. **Spread across session medians:
3.676%** of the overall median. Across all 20 repetitions the range is
33.443–37.556 ns/message.

With the cell held fixed, this 3.7% is **temporal**: it is the same
configuration measured at four different points in time on an unpinned,
non-quiesced host. It is the error bar on the published figure and it must be
quoted with it. No claim of a controlled thermal or frequency regime is made.

Note that session 1 is the fastest and the sessions do not drift
monotonically — consistent with ordinary host activity rather than with a
systematic warm-up or thermal trend. **REASONED**, not measured: the dataset
records no temperature, no frequency and no core placement.

### 4.3 The workload is the same in every session

The analyzer enforces that all four sessions used the same `chunk_bytes`,
`queue_capacity`, `seed`, `snapshot_messages`, `live_messages` and
`total_messages`, and that all four computed the same reference checksum. They
did. A dataset whose sessions measured different workloads is refused rather
than averaged.

### 4.4 Retry diagnostics — and why they do not name a bottleneck

Over the 20 measured repetitions (**MEASURED**):

| counter | sum | min | max | repetitions with a nonzero value |
|---|---|---|---|---|
| `producer_full_retries` | 126,314 | 0 | 38,322 | 5 of 20 |
| `consumer_empty_retries` | 420,762,731 | 17,295,286 | 25,741,614 | 20 of 20 |

Pooled over the whole dataset, the consumer's failed pops outnumber the
producer's failed pushes by roughly **3,331 : 1**. Per session median,
`producer_full_retries` is 0 in all four sessions while
`consumer_empty_retries` is 20.1–22.7 million.

**The plain reading:** under this workload the consumer's `try_pop` finds the
ring empty about 4.2 times per live message, while the producer almost never
finds it full — and on the five repetitions where it does, the count is three
orders of magnitude smaller. Consumer-side queue-empty retry pressure dominates
producer-side queue-full retry pressure in this cell.

**What is NOT claimed.** These counters do **not** identify a bottleneck, and
this document does not use them to do so:

- A failed `try_pop` is not a unit of time. It says a pop found the ring empty;
  it does not say how long anything took, and it cannot be converted into a
  delay without a measurement this phase deliberately does not take.
- Each side's retry loop is inside the timed region, so both counters are
  partially **consequences** of the interval's own contention as well as causes
  of its length. They are not independent variables.
- **No causal claim about cache coherence, cache-line contention or memory
  ordering is made from these counters.** The counters do not observe caches,
  coherence traffic, core placement or memory ordering. Reading them as
  evidence for any specific microarchitectural mechanism would be an
  attribution the data cannot support.

**One observed relationship, reported descriptively (MEASURED).** Across the 20
repetitions, `consumer_empty_retries` correlates with `elapsed_ns` at Pearson
r = 0.747, while `producer_full_retries` correlates at r = 0.430. This is a
description of the data, not a causal finding — both quantities are partly
driven by the same interval length, and neither correlation is offered as
evidence for a mechanism.

### 4.5 The composition is not the sum of its parts

**REASONED from the MEASURED data.** The eight stages of §1.2 all run inside the
interval, and the two retry loops — which have no counterpart when the same
stages are run sequentially on one thread — contribute 420.9 million failed
operations across the dataset. The measured rate is therefore a property of the
**composition**, and nothing in this dataset licenses the statement that it
equals (or should equal) the cost of the stages measured separately.

Phase 3A does **not** decompose the figure into per-stage costs, and deliberately
does not: adding single-threaded decode-only or apply-only legs would be a
different measurement with different provenance, and §12 of the brief confines
this phase to one cell. Decomposition is a separate phase.

## 5. DERIVED — what the baseline establishes

**Q1. What rate does the integrated path sustain?**
28,646,780 messages/second (34.909762 ns/message), median of four session
medians, on the Apple M3 Max under the §2.2 workload. **MEASURED.**

**Q2. How repeatable is that figure on this host?**
Session medians span 3.676%. Across all 20 measured repetitions the range is
33.443–37.556 ns/message. The figure is stable enough to be a baseline and
variable enough that it must always be quoted with its spread. **DERIVED.**

**Q3. Are the correctness properties preserved at this rate?**
Yes, on every one of the 20 measured repetitions and on every warm-up: all
5,000,130 messages decoded, enqueued and consumed; the final book state, all
twenty pipeline counters, and the folded checksum identical to the
single-threaded reference, in all four sessions. **MEASURED.**

**Q4. Which retry pressure dominates this cell?**
Consumer-side queue-empty pressure, by roughly 3,331 : 1 pooled, with no session
where the producer's full-queue pressure was comparable. No bottleneck is
attributed and no mechanism is claimed — see §4.4. **MEASURED + the stated
limits.**

**Q5. Does this number transfer to anything else?**
No. See §6. **REASONED.**

## 6. INTERPRETATION

### 6.1 What the dataset supports

- A reproducible, verified **baseline** for the integrated path on this host
  under one documented workload, with the spread across sessions reported.
- Evidence that the correctness properties established in Phases 1A, 1B and 2
  **survive at 28.6 M messages/s** — every repetition matched the reference.
- A documented diagnostic asymmetry between the two retry counters, offered as
  a starting point for a later phase, not as a conclusion.

### 6.2 What this dataset explicitly does not claim

- That this rate is **exchange throughput**, **production trading throughput**,
  or **wire-to-exchange latency**.
- That it is a property of the pipeline alone. It is **workload- and
  host-specific**, and both were changing conditions: an unpinned,
  non-quiesced host at load average ~3, and one synthetic 12%-delete L2 mix.
- That any component of the path is a bottleneck.
- That the figure is comparable to any Phase-2 or Phase-3 figure. A Phase-2
  message is a raw payload on an empty queue; a Phase-3A message is framed,
  decoded, sequenced and **applied to a live order book**.
- That a different chunk size, queue capacity, book, queue variant or workload
  would give this rate.

## 7. LIMITATIONS

### 7.1 No thread placement is controlled

No affinity, no pinning, no thread priority. macOS may migrate either thread
mid-run and the two threads may land on different core types. No measurement in
this dataset observes which cores were used, so **no result here may be
attributed to a core type**.

### 7.2 The host was not quiesced

Load average ~3 on 14 logical CPUs throughout. This is ordinary desktop
background activity and it is the ambient condition, but it is uncontrolled: the
pre-flight check only refuses a *saturated* host, and it cannot see load that
arrives after it is read.

### 7.3 Both retry loops are inside the measurement

`ns/message` includes the producer's queue-full retry loop and the consumer's
queue-empty retry loop. It is **not** a queue residence time and **not** a
per-call `try_push`/`try_pop` cost. This is stated in `command.txt` and in the
benchmark's own usage text, and it is a property of the measurement rather than
a defect in it: a dropped message would be a lost sequence number, so
retry-until-success is the frozen design.

### 7.4 Thread wake-up is not fully excluded

The interval opens at the gate store; each thread begins its measured work when
it observes that store. Gate-observation latency per thread is therefore inside
the interval. It is small against a ~170 ms window, but it is not zero and this
document does not claim it is.

### 7.5 One cell, one workload, one host

No chunk-size axis, no capacity axis, no second book, no second queue variant,
no second workload, one host. Every one of those is a legitimate next
measurement and none of them was taken here.

### 7.6 Time is read twice per repetition

Session-granular timing only. Any statement about the *distribution* of cost
within a repetition — or about any individual message — is out of scope and
unsupported by this dataset.
