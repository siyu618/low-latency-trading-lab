# Experiment 03, Phase 3A — integrated market-data pipeline throughput (Apple M3 Max)

The canonical **end-to-end throughput baseline for the integrated market-data
path**: a pre-generated byte stream framed by `StreamDecoder`, decoded by the
frozen Phase-1B `decode_one`, handed across Experiment 02's selected
`SpscSeparatedBaselineRingBuffer<MdMessage, 4096>`, sequenced by
`MarketDataPipeline` and applied to Experiment 01's `FlatOrderBook`, as one
two-thread system.

Analysis and methodology: `docs/MARKET_DATA_THROUGHPUT.md`.

**Status: Phase 3A IMPLEMENTED / MEASURED.** Phase 3 is **NOT** complete; Phase
3B is not started. Measured 2026-09-15 on the Apple M3 Max development host.
Every number here comes from a real run; nothing is interpolated, estimated, or
copied from elsewhere.

## What is measured

`messages_per_second` = **live messages consumed / elapsed_ns**, where `elapsed`
runs from the **release of the start gate** to the **consumer's final apply**,
stamped by the consumer thread itself.

It **includes** stream framing across chunk boundaries, binary decode, message
construction, the queue handoff, the producer's queue-full retry loop, the
consumer's queue-empty retry loop, sequence validation, staging bookkeeping and
the `FlatOrderBook` apply.

It is **not** a latency, **not** a percentile and **not** a per-message cost.
The clock is read twice per repetition at session granularity; there is no
per-message timestamp, no timestamp field on `MdMessage`, and no side timestamp
array.

It is also **not** exchange throughput, **not** production trading throughput
and **not** wire-to-exchange latency. It is one synthetic workload on one host,
comparable only to another run of the same tool with the same workload on the
same host.

## Configuration — ONE cell

| property | value |
|---|---|
| source chunk size | 64 KiB, final chunk naturally shorter |
| SPSC capacity | 4096 |
| queue | `SpscSeparatedBaselineRingBuffer` (Experiment 02's frozen selection) |
| book | `FlatOrderBook` (Experiment 01, frozen) |
| pipeline | `MarketDataPipeline` (Experiment 03 Phase 1A, frozen) |
| decoder | `StreamDecoder` + `decode_one` (Phase 1B, frozen) |

**The chunk size and capacity are compile-time constants, not options.** The
benchmark's parser refuses unrecognised flags, so `--chunk-bytes` and
`--capacity` cannot be produced by accident.

**Phase 3A compares nothing.** It does not compare cached vs baseline SPSC
(Experiment 02 Phase 3B), SameLine vs Separated (Phase 3A), Flat vs Map
(Experiment 01), multiple capacities, or multiple chunk sizes. Those are
separate phases with separate result directories.

**Phase-2 and Phase-3 SPSC numbers are NOT comparable to these.** A Phase-2
message is a raw payload on an empty queue; a Phase-3A message is framed,
decoded, sequenced and applied to a live order book.

## Workload

Deterministic, seeded, generated **in full before any clock starts**.

| property | value |
|---|---|
| seed | `0x5EEDC0FFEE` |
| snapshot | `SnapshotBegin` + 64 bid + 64 ask levels + `SnapshotEnd` = 130 messages |
| mid price | 100000 |
| levels per side | 64 (128 price slots) |
| live messages | 5,000,000 `Level` messages |
| total messages | 5,000,130 |
| set / delete mix | 4,400,492 sets / 599,508 deletes (11.99%) |
| price domain | `[1, 200000]` — `FlatOrderBook`'s default domain |
| encoded size | 145,003,736 bytes |
| 64 KiB chunks | 2,213 |

**This does not model any specific real exchange's message distribution.**

The initial snapshot is applied **before** the timed interval and is excluded
from every published figure, so the timed region contains no malformed bytes, no
sequence gap, no stale message, no snapshot recovery, no terminal decode error
and no truncated input.

## The run design

4 sessions, one process each, run back-to-back. Each process runs 1 **excluded
warm-up** repetition and then 5 **measured** repetitions.

**The four sessions are sequential and are NOT independent trials.** There is
one cell, so there is no AB/BA counterbalance to apply — a counterbalance needs
two treatments. What the sessions give is a read on temporal drift: with the
cell fixed, all variation between session medians is temporal.

**Published figure:** the per-session median of the 5 measured repetitions, then
the median across the 4 session medians.

**Every raw repetition is preserved and none is discarded.** Repetitions are
never pooled into one giant observation.

## Headline result

| quantity | value |
|---|---|
| **`ns/message`** (median of session medians) | **34.909762** |
| **`messages/second`** (median of session medians) | **28,646,780.764** |
| messages processed per repetition | 5,000,000 |
| elapsed per repetition | 167–188 ms |
| measured repetitions | 20 (4 sessions × 5) |
| spread across session medians | **3.676%** |
| range across all 20 repetitions | 33.443–37.556 ns/message |

Per-session medians (`ns/message`): 34.102708 / 35.386125 / 35.162250 /
34.657275.

`median_messages_per_second` is **not** `10⁹ / median_ns_per_message`: each is
the median of its own per-repetition series, and the reciprocal of a median is
not the median of reciprocals. Both are reported as medians of their own series.

## Retry diagnostics (MEASURED)

| counter | sum over 20 reps | min | max | nonzero reps |
|---|---|---|---|---|
| `producer_full_retries` | 126,314 | 0 | 38,322 | 5 of 20 |
| `consumer_empty_retries` | 420,762,731 | 17,295,286 | 25,741,614 | 20 of 20 |

Consumer-side queue-empty pressure dominates producer-side queue-full pressure
by roughly **3,331 : 1** pooled.

**These counters do not identify a bottleneck**, and no causal claim about cache
coherence, contention or memory ordering is made from them. A failed `try_pop`
is not a unit of time, and both loops are themselves inside the measured
interval. See `docs/MARKET_DATA_THROUGHPUT.md` §4.4.

## Correctness

All 20 measured repetitions, and all 4 excluded warm-ups:

- `terminal_error == false`; the whole-stream decode and `framer.finish()`
  both returned `Ok` — no truncation, no malformed bytes
- `decoded_messages == enqueued_messages == consumed_messages == 5,000,130`
- live messages consumed == 5,000,000
- state, `last_applied_seq`, `expected`, best bid, best ask, `level_count`, all
  twenty pipeline counters, and the folded checksum identical to the
  single-threaded reference
- reference checksum `0x7E6BA57E42B53319`, **identical in all four sessions**

Before any clock started, the **frozen `ThreadedMdPipeline`** was run over the
same bytes and required to agree with the single-threaded reference on every
observable and all twenty counters. A repetition failing any of the above makes
the process exit 4 and no figure is published.

## Data files

- `raw/sessionN.csv` — **the primary data**: one row per measured repetition
  (5 rows each). Columns: `rep`, `live_messages`, `elapsed_ns`,
  `ns_per_message`, `messages_per_second`, `decoded_messages`,
  `enqueued_messages`, `consumed_messages`, `producer_full_retries`,
  `consumer_empty_retries`, `checksum`, `correctness`.
- `summaries/sessionN.txt` — the per-process summary exactly as reported by the
  benchmark (its own median / min / max / spread over that process's 5
  repetitions), followed by the same 5 rows.
- `stderr/sessionN.txt` — the benchmark's progress log, including the excluded
  warm-up repetition.
- `SUMMARY.csv` — **the derived cross-session table**: per-session medians, the
  published median of session medians, the spread, the retry diagnostics, and
  every raw repetition appended verbatim.
- `command.txt` — the exact invocations, in the order they ran, recorded by the
  runner as it ran them rather than reconstructed afterwards.
- `SESSIONS.md` — the session design, stated plainly.
- `HOST.md` — host and toolchain metadata, the load average at start and end,
  and the sha256 of every source file that produced the dataset.
- `invariants.txt` — the analyzer's verification record.
- `run_order.txt` — the execution order parsed back out of `command.txt`.

`SUMMARY.csv` is produced only **after** every session passes, and the analyzer
is the authoritative gate: it re-derives each headline from the raw rows,
refuses the dataset if any two sessions disagree on workload or reference
checksum, refuses it if any repetition's decoded/enqueued/consumed counts differ
from the expected total, and refuses it if any session's slowest repetition
exceeds 5× its own fastest.

## How it was measured

```sh
scripts/market-data-throughput.sh            # 4 sessions, canonical
FORCE=1 scripts/market-data-throughput.sh    # overwrite
SMOKE=1 scripts/market-data-throughput.sh    # tiny, non-canonical
```

Then verified and derived:

```sh
python3 scripts/analyze-market-data-throughput.py docs/results/market-data-throughput
```

No measurement in this dataset observes which cores were used, so no result here
may be attributed to a core type. The host was **not** quiesced beyond the

must not be quoted as a property of the pipeline alone. Full metadata:
`HOST.md`.

## Notes

- The components under test are **frozen**. None was modified to move a number.
- Phase 3A measures **throughput only**. P50 / P90 / P99 / P99.9 and any
  per-message timestamp are out of scope and are not present in the tooling or
  the dataset.
- Phase 3A does **not** decompose the figure into per-stage costs. Adding
  single-threaded decode-only or apply-only legs would be a different
  measurement with different provenance.
- The benchmark's smoke cell passes under ThreadSanitizer, with a verified
  positive control: an injected post-gate cross-thread write is detected
  (exit 134), so the clean run is a genuine negative. Sanitized runs produce no
  published number.
